# Release Plan

This document defines how changes move from development to `main`, how versions
are selected, and how users can see what changed. It applies to maintainers,
contributors, and automation.

## Goals

- Every pull request states whether it has no release impact or is a patch,
  minor, or major change.
- Agents prepare user-facing changes and exact-commit test evidence in a draft
  pull request; one final human PR approval follows click-through validation in
  the ServiceNow and Microsoft 365 test environments.
- `package.json`, `package-lock.json`, and the Microsoft 365 app manifest always
  carry the same semantic version.
- `CHANGELOG.md` is the source for curated user-facing release notes.
- Version tags create GitHub Releases automatically.
- Microsoft 365 organizational catalog publication remains a separate,
  explicitly approved operation.

## Canonical Version

The project uses one SemVer version in all of these files:

- `package.json`
- `package-lock.json` (top-level `version` and `packages[""]`)
- `m365-agent/appPackage/manifest.json`

Run `npm run release:check` to verify parity. Version `1.1.6` is the historical
baseline; the first release fully managed by this process will be `1.1.7` or a
higher minor/major version, depending on accumulated changes.

## Release Impact

Every pull request must select exactly one impact in the PR template.

| Impact | Use when | Examples |
| --- | --- | --- |
| **None** | No shipped user behavior changes | Documentation, tests, development-only dependencies, CI maintenance |
| **Patch** | Backward-compatible correction | Bug fix, security fix, accessibility fix, dependency update shipped at runtime |
| **Minor** | Backward-compatible capability | New MCP tool, widget, workflow, optional configuration, substantial UI capability |
| **Major** | Existing users must adapt | Tool removal/rename, incompatible schema, changed auth contract, removed configuration, support-policy break |

When several changes are released together, the highest impact wins. A major
change requires migration guidance in both the changelog and release notes.

Every PR also selects exactly one kind: **Regular change** or **Version
release**. Regular changes add notes and impact markers to `Unreleased`.
Version-release PRs are generated by `release:prepare`; CI verifies their actual
version delta and dated changelog section against the selected impact.
The one-time **Version baseline alignment** kind exists only to reconcile npm
metadata from `1.0.0` to the already deployed M365 baseline `1.1.6`; CI rejects
it for any other version pair.

## Pull Request Contract

Agents may open or update a draft PR while validation is in progress. Before a
user-facing PR is approved and merged:

1. Build and test locally.
2. For user-facing behavior, deploy the exact commit to `snowmcpwidg-dev` and
  complete hands-on testing in the developer/test Microsoft 365 agent, then
  verify the corresponding result or side effect in the ServiceNow test
  instance.
  Release/CI tooling that cannot affect the deployed application instead uses
  **Completed maintainer workflow review** with executable evidence.
3. Record the exact SHA and non-secret evidence in the PR, then obtain one final
  approving PR review. Do not push another commit after approval; stale review
  dismissal intentionally requires the gate again after any change.
4. Add one concise user-facing sentence to `CHANGELOG.md` under `Unreleased`.
  Add `<!-- release-impact: patch|minor|major -->` beside that entry so the
  highest queued impact remains machine-readable after merge.
5. Copy that sentence into the PR's **Release note** section.
6. Select one release impact and one human-validation state.
7. Include validation evidence or explain why no user-facing validation was
   required.

This is the single development approval gate. Agents own implementation,
automated checks, test deployment, evidence preparation, and draft PR updates.
Tenant admin consent, organizational catalog approval, production deployment,
and public communications remain separate privileged operations and are never
automatic consequences of this gate.

CI runs `release:check` and `release:pr-check`. It rejects ambiguous impact,
missing evidence, version drift, a missing changelog update, or release-note
text that does not match `Unreleased`.

Dependency PRs follow the same contract. Use **None** only for development-only
maintenance. A runtime dependency fix is normally **Patch** and needs a
changelog entry.

## Main Branch Release Queue

Merged release-bearing PRs accumulate under `CHANGELOG.md` → `Unreleased`.
Maintainers can preview the next version without changing files:

```bash
npm run release:plan -- --type patch
npm run release:plan -- --type minor
npm run release:plan -- --type major
```

The command prints the current version, proposed version, requested and highest
queued release types, and curated pending notes. It refuses a release type below
the highest merged marker. Release timing is maintainership-driven:

- Patch releases: as needed for fixes and security updates.
- Minor releases: when a coherent backward-compatible capability is ready.
- Major releases: only with migration guidance and an explicit support plan.

## Preparing a Release

Create a release branch from current `main`, then run:

```bash
npm run release:prepare -- --type <patch|minor|major>
```

This command:

1. Calculates the next SemVer version.
2. Synchronizes all canonical version files.
3. Moves `Unreleased` entries into a dated version section.
4. Creates a fresh empty `Unreleased` section.

Review the diff, run `npm run build && npm test`, and open a release PR. Select
**Version release** and the actual Patch/Minor/Major impact. Its validation
evidence must list the included PRs, completed tenant validation, and test
results.

After the release PR merges, tag that exact `main` commit:

```bash
git tag -s vX.Y.Z -m "Release vX.Y.Z"
git push origin vX.Y.Z
```

Use an annotated tag if signed tags are unavailable. The `release.yml` workflow
checks tag/version parity, rebuilds, reruns all tests, extracts the matching
changelog section, and creates the public GitHub Release.

## Microsoft 365 Publication

A GitHub Release does not publish the agent to the organizational catalog.
After the package version has been released and the tenant-tested package is
approved for organizational distribution, run:

```bash
npm run release:publish -- \
  --environment snowmcpwidg-dev \
  --agent-environment <dev|prod>
```

Teams Admin Center approval is still required. Never run `release:publish` as an
automatic consequence of merging to `main` or creating a GitHub Release.

## Hotfixes and Rollbacks

- A hotfix is a patch release from current supported `main`.
- A rollback uses a PR and the same checks as any other change.
- If a released version is faulty, do not move or delete its tag. Revert the
  change and publish a new patch version with clear release notes.
- Never rewrite public release history to hide a failed release.

## Maintainer Checklist

- [ ] Every included behavior was human-validated where required.
- [ ] The highest merged PR impact determines the release type.
- [ ] `npm run release:plan -- --type <type>` shows the intended version.
- [ ] `npm run release:prepare -- --type <type>` changed only expected release files.
- [ ] Build, tests, release checks, and CodeQL are green.
- [ ] Release PR is merged before tagging.
- [ ] Tag exactly matches the canonical version.
- [ ] GitHub Release notes match the changelog.
- [ ] Organizational catalog publication, if any, has separate approval.
